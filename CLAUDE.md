# Tala

Renamed from Sema on 2026-11-04: the snap name `sema` was taken. The user registered `tala` (Old Norse "to speak"). Older notes below say Sema.

Unofficial snap of the official Nextcloud Talk desktop client (nextcloud/talk-desktop). It repackages Nextcloud's unmodified Linux ZIP. There is no app code here: to change app behavior, contribute upstream.

Status is kept in this file.

## Recipe notes
- Version and ZIP sha256 are pinned in `snap/snapcraft.yaml`.
- The ZIP's top directory is mode 700, so `chmod -R a+rX app` in override-prime is required.
- The client hides its startup setting on Linux. `sema.autostart on|off|status` and the launcher right-click actions provide it.
- No NVIDIA env workaround is needed (tested on RTX 2080, Wayland, gpu-2404).
- Testing: build with `snapcraft pack`, `sudo snap install --dangerous`, then connect browser-sandbox, camera and audio-record by hand. `--remote-debugging-port=9222` exposes GPU and sandbox state over CDP.
- Build on skyfire only with at least 20G free on `/`, then `snapcraft clean`.

## Report a problem (built 2026-11-06, relay live)
The same design as XBTune's: menu item (plus the sign-in and keyring screens), dialog with optional text and contact and a "What gets sent" preview, a relay turning reports into issues labeled `user-report`, saved in `pending/` when sending fails (5 at most, 30 days, retried 15s after start), `close-stale-reports.yml`. App: `lib/src/report.dart`, `lib/src/report_view.dart`. Relay: `relay/bug-report/` with `worker.test.mjs`; the README lists setup. The Worker is live at `tala-bug-report.jimmy-tigert.workers.dev`, with a token limited to this repo's Issues (read and write). A test POST with curl created issue #5 with the right label and body, and it's closed.
Differences from XBTune: no AI check and no ECM. A `facts` field carries what the app checks: session, tray, snap permissions (`snapctl is-connected`), Nextcloud and Talk versions. The repo is public, so issues are public and the dialog says so. Masking is wider because many log lines quote raw errors: server and other hosts, URLs, room tokens, username, app password, email and IP addresses, home folders (`maskReportText`). Never add names or message text to `log()`: masking can't recognize them. Release stacks have no symbol names, so the fingerprint is the error type plus the message without digits. Network errors are logged but not offered as crashes.
Native crashes: `linux/runner/fatal_signal.cc` appends a line to `fatal.log` and hands on to the previous handler; only the signal's name is known, no stack. `log.txt` now persists across starts, rotating to `log.previous.txt`, so developer modes no longer wipe it.
Checked: 165 tests, relay tests with GitHub faked, SEGV and ABRT on the real build, `--crash-test`, `--report-check` against the real server (read-only, sends nothing), masking on 91 real log lines (nothing needed masking). `snap run tala --report-check` on 0.2.1 (2026-11-06): session, tray, permissions and server all correct. The host OS can't be read: AppArmor denies `/var/lib/snapd/hostfs/usr/lib/os-release` without `system-observe`, which isn't auto-connected, so a `Kernel:` fact from `/proc/version` stands in. XBTune's profile has no such rule either. Not checked: a report sent from the app itself, the dialog on screen, `snapctl` and host OS detection in a real snap (`snap run tala --report-check`).

## Guest links (confirmed by the user on 0.2.2, 2026-11-06)

## Internal signaling (built 2026-11-06, HPB calls confirmed still working on 0.3.1)
For servers with no HPB. `lib/src/internal_signaling.dart` is the transport (long poll and POST on `signaling/{token}`, using the room-join cookies); `Signaling` and it share `CallSignaling`. Mesh logic is in `call.dart`: `meshRole` follows the web client (larger session id offers, the waiting side re-offers every 10s, someone with no streams is only ever offered to). One connection carries both directions, so everything arriving before media is ready is held, and `freshMeshMessages` keeps only each person's newest offer, because the web client re-offers while it waits. Messages are handled one at a time: a candidate must not overtake its offer. Refactoring touched the HPB path too (`_sig` assignment, `_sendStatus`); the user confirmed a normal HPB call on 0.3.1.
Checked with a throwaway server (`tool/mesh-check/up.sh`, same Talk 24.0.7) and Talk's real web client under Playwright with a fake camera, using `tala --call-check --call-check-audio` (`TALA_CHECK_*` env, including `TALA_CHECK_MEDIA_DELAY`): Tala offering and answering, no media, Tala to Tala, three people, and a slow camera (5 of 5 after a fix; before it, the case where Tala should offer stuck with no audio). Real camera and mic with the user's OK on 2026-11-06 (`--call-check-camera`, byte counts only; the web client never takes screenshots): video reached the browser and decoded. Not checked: a real no-HPB server, NAT or TURN, more than three people. The test server's SQLite gives a 500 on most first polls, so retries start at 1s.

## Chat, first slice (built 2026-11-06, user confirmed sending and receiving both ways)
`lib/src/chat.dart` holds the model and `ChatThread` (long poll, paging, sending, read marker); `lib/src/chat_view.dart` holds the screens, with no new dependencies. ## Tray and background (built 2026-11-06)
User confirmed on 2026-11-06: the close button keeps Tala in the tray.
Native, no pub packages: `linux/runner/tray.cc` uses libayatana-appindicator (build needs `libayatana-appindicator3-dev`). `tray_manager` and `window_manager` were rejected: they moved onto the young `nativeapi` in late 2026 with several releases a week, and `system_tray` was last released in April 2023. The library warns at runtime that it's deprecated for libayatana-appindicator-glib; revisit when distributions ship that widely. Closing the window hides Tala only while a tray host is connected, otherwise it quits. The app is now unique on D-Bus, so a second launch brings up the running copy; launching with any argument (developer modes) stays separate. Tray Quit hangs up an active call first (3s limit in Dart, 5s in the runner). An incoming call shows a hidden window. `lib/src/tray.dart` is the Dart side, on channel `tala/tray`. `tool/install-desktop.sh` adds a launcher for the local build (installed on skyfire).
Verified by me: `tala --tray-selftest` (closes the window through the same path as its close button, Dart keeps running while hidden, drawing resumes on show), icon registered with the watcher, menu Quit over D-Bus exits cleanly, second launch leaves one copy. Not verified: tray Open clicked by hand, how the icon looks in the top bar, a call ringing a hidden window, Quit during a call. A snap must ship the library and needs a D-Bus name for the unique app. Mac and Windows need their own tray code. "Start at login" in the app menu (moved from the tray on 2026-11-06 at the user's request; off by default) writes `~/.config/autostart/<app id>.desktop` running `tala --background`, which stays hidden, or shows the window if no tray host appears in 20s. A snap must do autostart its own way.
